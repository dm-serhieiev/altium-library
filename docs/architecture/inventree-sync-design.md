# Архітектура inventree-sync: InvenTree → Microsoft Access → Altium DbLib

Статус: проєкт структури Python-програми, а не реалізований скрипт.

Назва програми та console command — `inventree-sync`, назва Python-пакета — `inventree_sync`. Синхронізація одностороння: InvenTree є джерелом істини, файл Microsoft Access `.accdb` — відтворюваною проміжною базою для Altium DbLib. Скрипт читає InvenTree і не змінює його категорії або компоненти.

## 1. Контракт і джерела правил

Документи `inventree-category-structure.md`, `ipn-naming-convention.md` і `library-convention.md` у цій папці описують правила проєкту для людини, але не є джерелом структури компонентної бази під час експорту і не парсяться програмою. InvenTree є єдиним джерелом істини для дерева категорій, Parts, шаблонів параметрів, призначень параметрів категоріям, значень параметрів, одиниць і choice lists. Скрипт не дублює ці дані в конфігураційних або інших версіонованих файлах репозиторію.

Поточні вимоги мають пріоритет над розділами 15–16 `library-convention.md` і прикладами розділу 13 `ipn-naming-convention.md`: використовуємо саме `Altium Symbol = бібліотека:символ` і `Altium Footprint = бібліотека:посадкове_місце`. Старі назви `Symbol`/`Footprint` та значення без бібліотеки автоматично не підставляються. Решта правил найменування зберігається. Переміщення моделі між файлами тепер потребує оновлення її параметра в InvenTree.

- Одна кінцева категорія → одна користувацька таблиця Access, включно з порожніми категоріями. Назва таблиці точно дорівнює `category.name`, без aliases, префіксів і суфіксів.
- Один InvenTree Part → один рядок. Stock Item, Supplier Part і Manufacturer Part не створюють додаткових рядків.
- `Part.IPN` → колонка `IPN`, ключ і назва компонента у базі Altium. `Part.name` не використовується як заміна.
- Інші поля компонента беруться з його параметрів. Виняток — чотири технічні колонки, обчислені з двох посилань на моделі.
- IPN не генерується заново і не розбирається для отримання Value, Package чи електричних характеристик.
- За замовчуванням експортуються всі Parts у вибраному дереві; фільтри active/template/virtual можливі лише явно в конфігурації, із кількістю виключених записів у звіті.
- Компонент без категорії або безпосередньо в некінцевій категорії — помилка перевірки області експорту. Його не розподіляємо довільно між дочірніми категоріями.

## 2. Структура програми

Пропонована структура всередині наявної папки `tools`:

```text
tools/inventree-sync/
├── pyproject.toml
├── config.example.toml
├── src/inventree_sync/
│   ├── __init__.py
│   ├── __main__.py        # виклик CLI
│   ├── cli.py             # validate/sync, коди завершення
│   ├── config.py          # TOML, env, перевірка конфігурації
│   ├── api.py             # HTTP, auth, timeout, retry, pagination
│   ├── adapters.py        # особливості версій REST API
│   ├── models.py          # dataclass: Category, Part, ParameterTemplate, Assignment, Parameter, ModelRef
│   ├── categories.py      # дерево, предки, листки, перевірка назв таблиць
│   ├── schema.py          # динамічна схема з InvenTree → колонки
│   ├── transform.py       # параметри → рядок, розбір Altium refs
│   ├── validate.py        # цілісність, дублікати, правила експорту
│   ├── access.py          # ODBC, DDL, параметризований запис і перевірка ACCDB
│   ├── report.py          # JSON-звіт і маніфест категорій/полів
│   └── pipeline.py        # послідовність експорту
└── tests/
    ├── fixtures/          # знеособлені відповіді підтримуваних API
    ├── test_api.py
    ├── test_categories.py
    ├── test_transform.py
    └── test_sync.py
```

Залежності: Python 3.11+ (`tomllib`, `dataclasses`, `argparse`, `pathlib`, `logging`), `requests` для HTTP, `pyodbc` для Access, `pytest` для тестування. Цільове середовище запису — Windows із драйвером Microsoft Access Database Engine відповідної розрядності. Версії залежностей фіксуються після перевірки реалізації.

Для сучасного 64-бітного Altium обираємо 64-бітні Python та ACE; на початку перевіряємо доступність драйвера `Microsoft Access Driver (*.mdb, *.accdb)`. Access Runtime включає ODBC/OLE DB-компоненти, але його сумісність із установленим Office потрібно перевірити перед установленням. [Microsoft Access Runtime](https://support.microsoft.com/en-us/access/download-and-install-microsoft-365-access-runtime), [розрядність рушія для Altium](https://www.altium.com/documentation/altium-designer/components-libraries/database-libraries/using-32-64-bit-altium-designer-same-computer).

Основні контракти функцій:

```python
class InvenTreeClient:
    def iter_categories(self): ...
    def iter_parts(self): ...
    def iter_parameter_templates(self): ...
    def iter_category_parameters(self): ...
    def iter_part_parameters(self): ...

def build_category_tree(categories): ...
def effective_schema(category_id, tree, assignments, templates, parameters): ...
def parse_model_ref(value: str, kind: str) -> ModelRef: ...
def build_row(part, parameters, config) -> dict[str, str | None]: ...
def validate_dataset(dataset, config): ...
def validate_table_name(category_name: str) -> None: ...
def write_access_database(dataset, template, destination): ...
def sync(config) -> SyncReport: ...
```

HTTP-відповіді нормалізує `adapters.py`; решта програми не залежить від конкретного JSON API. Внутрішні індекси: `categories[pk]`, `parts[pk]`, `templates[pk]`, `category_parameters[category_pk]`, `parameters[part_pk][template_pk]`.

## 3. Авторизація і REST API

Основний спосіб — токен із змінної `INVENTREE_API_TOKEN`, заголовок `Authorization: Token <token>`. Альтернатива — HTTP Basic із username і паролем, отриманим через `getpass` або env. Basic надсилається лише через HTTPS. Не потрібні браузерний логін або збереження сесійних cookies. Токен, пароль і HTTP-заголовки не потрапляють у конфігурацію, Git або звіт. [Документація авторизації InvenTree](https://docs.inventree.org/en/latest/api/).

План запитів:

| Дані | Endpoint / стратегія |
|---|---|
| Версія і можливості | API root та схема конкретного сервера, доступна через його `/api-doc/` |
| Категорії | `GET /api/part/category/` |
| Компоненти | `GET /api/part/` |
| Призначення параметрів категоріям | `GET /api/part/category/parameters/` |
| Шаблони параметрів | `GET /api/parameter/template/` у сучасному API |
| Значення параметрів | `GET /api/parameter/` у сучасному API; фільтри `model_type` і, за потреби, `model_id` |

Маршрути категорій описані у [Parts API](https://docs.inventree.org/en/latest/api/schema/part/); універсальні параметри — у [General API](https://docs.inventree.org/en/latest/api/schema/general/). Значення `model_type` для Part та формат полів зв'язку перевіряються за схемою встановленої версії, а не вгадуються. Старі сервери можуть вимагати окремий адаптер параметрів Parts; непідтримувана схема завершує запуск до запису ACCDB.

Усі списки читаються повністю з пагінацією: підтримати `results/next` і непагінований масив, перевіряти повторення сторінок і `pk`. Абсолютний `next` дозволений лише для того самого origin і базового API-шляху; переходи HTTP на інший сервер заборонені. Використовувати query params клієнта для URL-кодування, зокрема `%` в IPN.

Завантажувати параметри пакетно там, де це дозволяє API; інакше — окремими запитами за Part із кешем шаблонів. Не припускати, що `/api/part/` містить усі параметри. Не довіряти неявній рекурсивності фільтра category: остаточна перевірка належності Part до leaf-category виконується локально.

HTTP-політика: перевірка TLS увімкнена, connect/read timeout, обмежені повтори GET для 429 і тимчасових 5xx із Retry-After/backoff; 401/403 — негайна помилка, без перемикання способу авторизації. Відсутність доступу не трактувати як порожню категорію. Обліковий запис повинен бачити все вибране дерево: невидимих через права дочірніх категорій клієнт самостійно виявити не зможе.

## 4. Категорії та таблиці Access

Листок визначається відсутністю дочірніх вузлів у повному доступному дереві InvenTree, а не рівнем вкладеності, назвою категорії чи кількістю Parts. Скрипт не містить локального списку кінцевих категорій і не використовує `inventree-category-structure.md` як runtime whitelist. Якщо дерево категорій змінюється на сервері, набір leaf-категорій і відповідних таблиць Access змінюється автоматично під час наступної повної синхронізації.

Назва кожної користувацької таблиці Access точно дорівнює фактичному `category.name`, отриманому з InvenTree. Поточні назви категорій можуть бути задокументовані окремо для людини, але документація не підміняє серверні дані і не бере участі у побудові схеми.

Правила проєкту для назв категорій, сумісні з Access:

- Від 1 до 64 символів; англійські літери, цифри й одиночні внутрішні пробіли. Формальна перевірка: `[A-Za-z][A-Za-z0-9]*(?: [A-Za-z0-9]+)*` плюс перевірка довжини.
- Без початкових/кінцевих пробілів, керувальних символів і пунктуації. Це свідомо вужчий набір, ніж усі дозволені Access символи; він усуває неоднозначності SQL та драйверів.
- Назви кінцевих категорій у всій області синхронізації мають бути унікальні без урахування регістру, навіть якщо вони розташовані в різних гілках.
- Зарезервовані слова Access/ACE та системні префікси `MSys`/`USys` не використовуються для категорій. Це технічне правило синхронізатора; відповідний список перевіряє валідатор програми.
- Скрипт не скорочує, не транслітерує і не додає PK до назв таблиць. Порушення — помилка з category PK і повним шляхом; виправлення має відбутися в InvenTree до синхронізації.

Access дозволяє імена об'єктів до 64 символів і підтримує пробіли. Власні назви SQL завжди обрамляються квадратними дужками після валідації, наприклад `[Fixed Resistors]`. Дужки не є частиною назви таблиці. [Правила Microsoft для імен](https://support.microsoft.com/en-us/access/guidelines-for-naming-fields-controls-and-objects), [створення й найменування таблиць](https://support.microsoft.com/en-us/access/create-a-table-and-add-fields).

Маніфест зберігає category PK/full path/table name для діагностики. Після перейменування категорії в InvenTree наступна повна синхронізація створює таблицю з новою назвою; mapping відповідної таблиці в DbLib також потребує оновлення. Попередня назва не зберігається як alias.

Службові дані записуються в JSON поруч, без додаткових користувацьких таблиць. Системні таблиці Access не є таблицями компонентів. Якщо в обраній області синхронізації немає жодної leaf-категорії, синхронізація завершується помилкою конфігурації/даних.

## 5. Схема колонок і успадкування

Схема кожної користувацької таблиці Access формується **динамічно з InvenTree**. Репозиторій не містить окремого списку загальних, батьківських або leaf-specific параметрів і не дублює одиниці чи choice lists.

Джерела схеми:

- `ParameterTemplate` з InvenTree — ім'я параметра та доступні метадані шаблону, зокрема одиниці й choices, якщо вони надані API;
- призначення шаблонів параметрів категоріям — визначають параметри, пов'язані з категоріями вздовж шляху від кореня області синхронізації до leaf-категорії;
- фактичні параметри всіх Parts у leaf-категорії — дозволяють не втратити параметр, який існує на Part, але не присутній серед отриманих призначень категорій.

Порядок технічних колонок фіксований: `IPN`, `Library Ref`, `Library Path`, `Footprint Ref`, `Footprint Path`. Після них ідуть параметри InvenTree у детермінованому порядку: спочатку параметри, призначені категоріям уздовж ancestry від кореня до листка, потім додаткові параметри, знайдені безпосередньо на Parts і ще не включені до схеми. Якщо API має явний порядок призначень, адаптер зберігає його; за його відсутності застосовується стабільний порядок за ідентифікатором шаблону, щоб два однакові знімки давали однакову схему.

Назви колонок параметрів залишаються точними іменами шаблонів InvenTree. Скрипт не перейменовує `Power Rating` у `Power`, `Mounting Type` у `Mount` тощо.

Для порожньої leaf-категорії колонки формуються лише з фактичних призначень шаблонів параметрів цій категорії та її предкам у вибраному дереві. Тому порожня категорія також отримує коректну схему без локального дублювання структури параметрів.

Для непорожньої leaf-категорії до цієї схеми додається об'єднання фактичних параметрів **усіх** її Parts, а не лише першого рядка.

Успадкування визначає **наявність колонки**, а не автоматичне значення. Значення завжди береться з параметра конкретного Part. Відсутній необов'язковий параметр → SQL NULL; default шаблону не підставляється приховано. Якщо InvenTree передає ознаку обов'язковості для призначення параметра категорії, адаптер зберігає її, а валідатор застосовує її до відповідних Parts; локальний список required-параметрів для звичайних полів не ведеться.

Повторне призначення того самого template PK в ancestry дає одну колонку. Два різні шаблони з однаковим ім'ям, дубль параметра Part або колізія імені параметра з технічною колонкою — помилка, без перезаписування значень. Одиниці та choice lists не нормалізуються й не копіюються в локальну схему-конфігурацію; за потреби вони використовуються безпосередньо з метаданих InvenTree для валідації та діагностики.

Єдиний спеціальний контракт поверх довільної схеми InvenTree — `Part.IPN` та параметри `Altium Symbol` і `Altium Footprint`, необхідні для формування DbLib-запису. Їх спеціальна семантика описана в наступному розділі; це правила експорту, а не дубль структури InvenTree.

## 6. Посилання на моделі та DbLib mapping

Приклади вхідних значень:

```text
Altium Symbol    = Passives:Resistor
Altium Footprint = Resistors:RES_0603_H0.55
```

Дозволити також явні розширення: `Passives.SchLib:Resistor` та `Resistors.PcbLib:RES_0603_H0.55`. Парсер вимагає рівно одну двокрапку та дві непорожні частини. Частина бібліотеки — basename без директорій; неправильне розширення, додаткова двокрапка чи шлях — помилка. Для назв застосовуються правила `library-convention.md`; двокрапка є роздільником, а не частиною назви. Windows drive path не є допустимим вхідним значенням.

При розташуванні `database/Components.DbLib` і `database/components.accdb`:

| Поле Access | Приклад | Mapping у DbLib |
|---|---|---|
| IPN | RES-10K-1%-0603 | ключ запису; параметр IPN |
| Library Ref | Resistor | [Library Ref] |
| Library Path | ..\symbols\Passives.SchLib | [Library Path] |
| Footprint Ref | RES_0603_H0.55 | [Footprint Ref] |
| Footprint Path | ..\footprints\Resistors.PcbLib | [Footprint Path] |
| Value | 10k | Value |
| Package | 0603 | Package |
| Mounting Type | SMD | Mounting Type |
| Resistance | 10 kΩ | Resistance |
| Tolerance | 1% | Tolerance |
| Power Rating | 0.1 W | Power Rating |

`IPN` — ідентифікатор запису бази, `Library Ref` — назва спільного символу. Вони не повинні збігатися. `Altium Symbol` і `Altium Footprint` також залишаються окремими вихідними колонками для простежуваності.

`Comment` або `Description`, якщо потрібні, беруться лише з однойменних параметрів Part, отриманих з InvenTree, і налаштовуються в mapping DbLib. Скрипт не вигадує їх із `Part.name`, `Part.description` або IPN. Mapping `Value` на Comment можна окремо налаштувати в DbLib як свідомий вибір.

Відносні шляхи обчислювати від папки цільового DbLib, не від робочої директорії процесу. Перевіряти існування файлів бібліотек. Перевірка наявності самого символу/footprint усередині бінарної бібліотеки потребує окремого Altium-індексу чи спеціалізованого парсера; перевірка файлу не доводить наявність моделі.

Повторне використання моделі багатьма Parts допустиме. Посилання на одну канонічну назву в різних бібліотеках — конфлікт згідно з правилами репозиторію, але повний пошук невикористаних дублів також потребує індексу бібліотек.

У DbLib підключити `database/components.accdb` через сумісний Access OLE DB/ODBC-провайдер, увімкнути таблиці кінцевих категорій, призначити ключ `IPN` та наведені mappings. Назви таблиць не мають суфікса `$`. Поля Access не містять квадратних дужок у своїх назвах — у колонці mapping вони позначають спеціальні цілі Altium. `.accdb` є джерелом даних; `.DbLib` окремо містить підключення й mapping. [Офіційна документація Altium](https://www.altium.com/documentation/altium-designer/components-libraries/database-libraries/creating-defining).

## 7. Схема і надійний запис Microsoft Access

Файл має формат `.accdb`. Для створення тимчасової бази копіювати заздалегідь підготовлений порожній Access-файл, заданий через `access.template`. Його потрібно один раз створити у Microsoft Access та зберегти як технічний шаблон без користувацьких таблиць, зв'язків, запитів і макросів. Нульовий файл із розширенням `.accdb` не є базою; ODBC-підключення не замінює її створення. Відсутній або некоректний шаблон — помилка preflight; шаблон не змінюється.

Підключення Python до тимчасової бази через `pyodbc`:

```text
DRIVER={Microsoft Access Driver (*.mdb, *.accdb)};DBQ=<absolute-path-to-staging.accdb>;
```

Рядок підключення будується з коректним ODBC-екрануванням значень. Шлях до бази не підставляється у SQL.

| Група полів | Тип Access | Правила |
|---|---|---|
| IPN | Short Text / `TEXT(255)` | NOT NULL, PRIMARY KEY; непорожній; унікальний також між таблицями |
| Library Ref, Library Path, Footprint Ref, Footprint Path | Short Text / `TEXT(255)` | обов'язкові непорожні значення; понад 255 символів — помилка |
| Параметри InvenTree, включно з Value, Package та вихідними Altium refs | Long Text / `LONGCHAR` | текст або NULL; без числового перетворення й обрізання |

Long Text для параметрів дозволяє не підбирати типи за першими записами й не втрачати довгі описи. Для таких полів не створюються індекси. Сумісність читання Long Text конкретним DbLib-провайдером перевіряється інтеграційним тестом. Якщо в майбутньому для окремого технічного випадку знадобиться Short Text, це має бути явним налаштуванням формату експорту, а не локальним дублем метаданих параметра InvenTree.

Значення `0603`, `1%`, `1E3` і `=...` передаються як Python `str`, а відсутнє/порожнє необов'язкове значення — як `None` → SQL NULL. Непорожні рядки не змінюються і не доповнюються апострофами. Одиниці залишаються частиною текстового значення.

Зберігати `data` параметра, а не числове `data_numeric`. Не змінювати одиниці, десяткові роздільники чи префікси автоматично; одиниці й choice lists, якщо вони потрібні для діагностики або перевірки, брати безпосередньо з метаданих ParameterTemplate/assignment, отриманих з InvenTree. SQL NULL не замінювати на `0` або текстові `None`/`NaN`.

Назви полів — точні назви параметрів; вони перевіряються на обмеження Access, довжину до 64 символів і колізії без урахування регістру. Конвенція назв категорій не перейменовує поля параметрів. Неприпустимі назви — помилка, без автоматичних aliases. Імена таблиць/полів обрамляються `[...]`; значення передаються виключно через placeholders `?`:

```sql
INSERT INTO [Fixed Resistors] ([IPN], [Package], [Value]) VALUES (?, ?, ?)
```

Ідентифікатори не можна передати як SQL-параметри, тому їхня валідація обов'язкова перед побудовою DDL/DML. Заголовки є полями схеми; додатковий запис із назвами полів не створюється. Access не гарантує порядок записів: читати з `ORDER BY [IPN]`, якщо потрібен стабільний порядок.

Враховувати ліміти Access: максимум 255 полів у таблиці, 255 символів у Short Text і 2 GB на файл мінус системні об'єкти. Контролювати розмір бази та помилки місткості записів/рушія; жодне перевищення не призводить до обрізання або часткової публікації. [Специфікація Microsoft Access](https://support.microsoft.com/en-us/access/access-specifications).

Кожен запуск формує повний знімок: копіювати порожній шаблон у тимчасовий `.accdb` у директорії результату, створити схему, вставити дані з `autocommit=False`, виконати commit. При помилці — rollback записів і відхилення тимчасової бази; не покладатися на транзакційність DDL для захисту попереднього результату. Потім закрити з'єднання, повторно відкрити базу й перевірити точний набір користувацьких таблиць, типи полів, кількість записів, IPN та збережені значення.

Після перевірки закрити всі власні cursors/connections і атомарно замінити цільовий `.accdb` у тій самій файловій системі. Якщо Access/Altium утримує файл, завершитися з помилкою без видалення lock-файлів чи примусового закриття сторонніх процесів. Попередній файл зберігається. Паралельні запуски для одного destination забороняються власним блокуванням програми. Маніфест містить hash готового ACCDB для перевірки відповідності звіту.

Повна перебудова відображає видалення Parts, переміщення між категоріями та зміни схеми без застарілих записів. Вихідна база належить `inventree-sync`: ручні зміни в ній не є джерелом даних і будуть замінені наступною успішною синхронізацією.

## 8. Конфігурація та запуск

Приклад майбутнього `config.example.toml` (не готовий до запуску без реалізації):

```toml
[inventree]
base_url = "https://inventree.example.com"
auth = "token"
token_env = "INVENTREE_API_TOKEN"
connect_timeout = 10
read_timeout = 60
retries = 3

[scope]
root_category_path = ["Electronic Components"]
# Для повної бази scope можна явно переключити на all.

[sync]
output = "../../database/components.accdb"
dblib = "../../database/Components.DbLib"
include_empty_categories = true

[access]
template = "../../database/templates/empty.accdb"
driver = "Microsoft Access Driver (*.mdb, *.accdb)"

[libraries]
symbols = "../../symbols"
footprints = "../../footprints"
```

Усі файлові шляхи конфігурації відносні до самого TOML. Кореневий шлях категорії має знаходити рівно один вузол. У режимі всієї бази некатегоризовані Parts також перевіряються; у режимі піддерева звіт явно показує межу експорту. Конфігурація задає лише підключення, область синхронізації та технічні параметри експорту. Вона не містить списків категорій, параметрів, units, choices або успадкування: ці дані кожного запуску завантажуються з InvenTree.

Майбутній CLI:

```text
inventree-sync validate --config config.toml
inventree-sync sync --config config.toml
# Еквівалентний виклик Python-пакета:
python -m inventree_sync sync --config config.toml
```

`validate` перевіряє драйвер, шаблон, конфігурацію та завантажені дані без заміни ACCDB. `sync` повторює перевірки й публікує базу лише за відсутності помилок. На рівні контракту експорту завжди обов'язкові `IPN`, `Altium Symbol` і `Altium Footprint`. Для інших параметрів ознака required, якщо вона підтримується відповідною версією API, береться з InvenTree через адаптер; локального списку обов'язкових параметрів немає. Console command реєструється через `[project.scripts]` у `pyproject.toml`: `inventree-sync = "inventree_sync.cli:main"`.

## 9. Послідовність і контроль якості

```text
config + secrets
  → автентифікація і перевірка API
  → повне дерево категорій + Parts + ParameterTemplates + призначення категоріям + Part parameters
  → перевірка дерева, області та унікальності IPN
  → динамічна успадкована схема кожного листка з даних InvenTree
  → перетворення посилань і рядків
  → перевірка всього набору
  → тимчасовий ACCDB → DDL + INSERT → commit → повторне читання
  → закриття з'єднань → заміна цільового ACCDB
  → JSON-звіт і маніфест
```

Помилки блокують публікацію всього файлу: пропущений/дубльований IPN (також колізія без урахування регістру для провайдера БД), дубль параметра, неправильне посилання, відсутня бібліотека, цикл/відсутній предок у дереві, невідповідна категорія, неповна пагінація чи збій HTTP. Стиль IPN перевіряється без автоматичного перейменування: історичні IPN та оригінальні ordering codes не переписуються за новими правилами.

JSON-звіт: час початку/кінця, версія програми та сервера/API, category PK/full path/table name, кількість отриманих і експортованих Parts, виключення, колонки та їх джерела в InvenTree, попередження/помилки із Part PK/IPN, hash результату. Жодних секретів. Багатозапитний REST-експорт не гарантує транзакційний snapshot: для узгодженого виробничого випуску потрібне вікно без редагувань або серверний snapshot. Часи збору фіксуються у звіті.

Коди завершення: `0` успіх, `1` неочікувана помилка, `2` конфігурація/дані, `3` API/авторизація, `4` файловий запис/блокування.

Тести реалізації:

1. Пагінація, 401/403, retry 429, непідтримувана схема, зовнішній/циклічний next.
2. Inductors як листок, порожні категорії, точна рівність category.name/table.name, назви до 64 символів, відхилення пунктуації й зарезервованих слів, дублікати назв у різних гілках, новий дочірній вузол і Part у колишньому листку.
3. Динамічні успадковані колонки з category assignments, порожня leaf-категорія без локальної схеми, параметр лише у другому Part, новий ParameterTemplate без змін репозиторію, одиниці/choices з API, відсутній параметр, повторний template PK і конфлікт назв.
4. Обидва формати бібліотеки з/без розширення, неправильний delimiter, Package не підміняє Footprint, різні IPN зі спільним символом.
5. Повторне читання ACCDB: `0603`, `%`, Unicode одиниць, апострофи і `=...` залишаються текстом; довгі значення не обрізаються; відсутнє значення є NULL; дубль IPN відхиляється; помилка або lock не змінює попередню базу.
6. Інтеграційна перевірка на Windows із конкретним InvenTree та Altium: ACE відповідної розрядності, видимість таблиць і Short/Long Text полів, пошук за IPN, розміщення символу та передача footprint на PCB. Перевірити два послідовні sync, видалення/переміщення Part, перейменування категорії і блокування файлу Altium.

Наразі сервер InvenTree, його версія та облікові дані не задані. API-контракт і вимоги Access звірені з офіційними джерелами. Реалізація програми, створення шаблону ACCDB, перевірка встановленого ACE та живої синхронізації з Altium залишаються наступним етапом.
